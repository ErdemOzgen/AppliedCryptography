## Required Reading Notes (Cryptography-Only Deep Dive)

### 1. What cryptography is
Cryptography is the discipline of enforcing security properties with mathematics and protocols, even when parts of the environment are untrusted. It is much broader than "encryption." At a systems level, cryptography gives you:

- Confidentiality: who can read data.
- Integrity: whether data was modified.
- Authentication: who created or sent data.
- Verifiability: proving facts or computations.
- Controlled delegation: letting others compute or store without giving away trust.

Senior engineer framing: cryptography is a trust-minimization toolkit. You use it so security does not depend on network honesty, server goodwill, or obscurity.

### 2. Cryptography is everywhere in modern systems
A phone, browser, and cloud app run cryptography continuously:

- WPA3 and cellular protocols protect link-level channels.
- TLS protects transport sessions.
- Signed code/update verification protects software supply chains.
- Secure hardware (Secure Enclave/TEE/HSM) protects key usage and storage.

Practical takeaway: cryptography is infrastructure, not a feature toggle. Therefore, implementation quality and key lifecycle discipline matter as much as primitive selection.

### 3. Real-world use cases mapped by security goal
Use cases should always be mapped to explicit goals:

- Confidentiality-heavy: messaging, VPN, encrypted storage.
- Authentication-heavy: TLS certs, SSH host keys, signed updates.
- Integrity-heavy: package verification, transaction validation, tamper detection.
- Privacy-preserving computation: private contact discovery, age predicates, ZK-based proofs.

Engineering lesson: never start with "which algorithm"; start with "which property under which threat model."

### 4. How cryptography becomes deployable security
The pipeline is:

1. Formal definitions and candidate constructions.
2. Cryptanalysis and adversarial review.
3. Standardization and interoperability.
4. Safe implementation and hardening.
5. Integration, deployment, and continuous audit.

Most real failures are composition bugs (API misuse, nonce reuse, key confusion, metadata leakage), not raw primitive breaks.

### 5. Primitives vs protocols
A primitive is a constrained component. A protocol is a composed system with end-to-end security claims.

- Primitive examples: AES, SHA-2, HMAC, Diffie-Hellman.
- Protocol examples: TLS, Signal, WireGuard, SSH.

A secure primitive does not automatically imply a secure protocol. Security is a property of the composition.

### 6. Core goals: confidentiality, authentication, integrity
These goals are distinct and must be stated separately.

- Confidentiality: attacker cannot learn plaintext.
- Authentication: receiver can verify origin/identity.
- Integrity: receiver detects tampering.

Critical nuance: encryption alone may not provide integrity. Malleable encryption without authentication is dangerous.

### 7. Advanced goal: post-compromise security
Two commonly confused properties:

- Forward secrecy (FS): compromise now does not reveal old traffic.
- Post-compromise security (PCS): after compromise ends, future traffic can recover through key evolution.

Signal-style ratcheting is a practical approach to achieving strong FS + PCS behavior in asynchronous messaging.

### 8. Why access control alone is insufficient
Access control answers "who is allowed." It does not guarantee:

- Secure transport against MITM.
- Server-side confidentiality if server is compromised.
- Cryptographic integrity guarantees.
- Verifiable origin in hostile networks.

So access control and cryptography are complementary, not interchangeable.

### 9. The "magic" capabilities of cryptography
Cryptography enables capabilities that appear impossible without it:

- Private communication over public channels.
- Zero-knowledge proving (prove claim, hide witness).
- Verifiable computation (prove execution correctness).

These capabilities are not mystical; they are formal guarantees under explicit assumptions.

### 10. Hardness assumptions and reduction-based security
Most modern schemes are computationally secure, not information-theoretically secure.

Security argument style:

- If attacker breaks scheme S, we build an algorithm that solves hard problem P.
- If P is infeasible for realistic resources, breaking S is infeasible.

This is reductionist reasoning. Always ask:

- Which assumption?
- Which model?
- Which adversary capabilities?

### 11. Diffie-Hellman key exchange mechanics
Given public parameters p and g:

- Alice picks secret a, sends A = g^a mod p.
- Bob picks secret b, sends B = g^b mod p.
- Shared secret: s = B^a = A^b = g^(ab) mod p.

Correctness comes from exponent laws. Security depends on discrete log / related assumptions and proper parameter choice.

Important: unauthenticated DH is vulnerable to active MITM. Authentication must be added (signatures, certificates, PSK, or authenticated AKE protocols).

### 12. Discrete logarithm problem (DLP)
Given g and h = g^x, finding x is believed hard in suitable groups.

- Forward direction (exponentiation): easy.
- Inverse direction (discrete log): hard.

This asymmetry powers classical DH and many signature systems.

Quantum caveat: large fault-tolerant quantum machines running Shor would break classical DLP-based systems.

### 13. Signal stack: X3DH and Double Ratchet
Signal separates initialization from continuous key evolution:

- X3DH: asynchronous authenticated key agreement using identity keys + prekeys.
- Double Ratchet:
  - DH ratchet for periodic fresh shared secrets.
  - Symmetric ratchet for per-message key derivation.

Security effects:

- Message-level forward secrecy.
- Recovery potential after compromise.
- Strong key separation across messages and directions.

### 14. Asymmetric vs symmetric primitives
Asymmetric cryptography:

- Public/private key pairs.
- Better for key establishment and signatures.
- Slower and often larger objects.

Symmetric cryptography:

- Shared keys (or unkeyed hashes).
- Very fast and ideal for bulk data.

Modern systems are hybrid: asymmetric for setup/authentication, symmetric for data plane encryption/authentication.

### 15. Kerckhoffs principle
A system should remain secure even if everything except the key is public.

Implications:

- Open scrutiny is a strength.
- Security-through-obscurity is fragile.
- Public standards and audited implementations improve assurance.

If secrecy of algorithm details is required for safety, the design is not robust.

### 16. Hash functions: what they do
A cryptographic hash maps arbitrary input length to fixed output length.

Expected behavior:

- Deterministic output.
- Efficient computation.
- Strong diffusion (small input change -> unrelated-looking digest).
- One-way resistance in cryptographic sense.

Hashing is not encryption. There is no "decrypt hash" operation.

### 17. Hash security properties
Three core notions:

- Collision resistance: hard to find m1 != m2 with H(m1) = H(m2).
- Preimage resistance: given h, hard to find m with H(m) = h.
- Second preimage resistance: given m1, hard to find m2 != m1 with same hash.

Password storage nuance:

- Plain fast hashes are insufficient for low-entropy secrets.
- Use memory-hard password hashing/KDFs (Argon2id preferred in modern designs).

### 18. Hash function applications
Common applications:

- Integrity fingerprints and content addressing.
- Merkle trees and authenticated data structures.
- Transcript binding in authenticated protocols.
- Commitments and ZK systems.
- Proof-of-work constructions.

But hash integrity checks require trusted distribution of expected digests, or signatures over digests.

### 19. Zero-knowledge proofs (ZKP)
A ZKP proves a statement without revealing the witness.

Security properties:

- Completeness.
- Soundness.
- Zero-knowledge.

Deployment perspective:

- Great for selective disclosure (e.g., age >= 18).
- Useful for verifiable computation and privacy-preserving blockchain validity.
- Security depends on protocol model, implementation correctness, and side-channel hygiene.

### 20. AES fundamentals
AES is a block cipher with:

- Block size: 128 bits.
- Key sizes: 128/192/256 bits.

It is modeled as a keyed permutation (PRP): reversible under the same key.

Operational reality: AES alone is not a full encryption solution; mode and nonce policy determine security.

### 21. Why ECB is insecure
ECB encrypts each block independently.

Consequence:

- Equal plaintext blocks -> equal ciphertext blocks.
- Structural patterns leak.

Thus ECB fails semantic security on structured data.

### 22. Modes of operation and AEAD preference
Classical modes:

- CBC: confidentiality with random IV, but requires separate integrity layer.
- CTR: stream-like behavior, but nonce reuse is catastrophic.
- CFB/OFB: stream conversions, less common in modern protocol design.

Modern default:

- Use AEAD schemes (AES-GCM or ChaCha20-Poly1305).
- In nonce-misuse-risk contexts, consider misuse-resistant designs (e.g., AES-GCM-SIV).

### 23. TLS 1.3 cryptographic composition
TLS 1.3 combines:

- Ephemeral (EC)DH for key agreement.
- Signatures/certificates for authentication.
- Hash-based transcript and HKDF key schedule.
- AEAD for record encryption + integrity.

This is textbook applied cryptography: multiple primitives with tightly bound state and transcript semantics.

### 24. TLS threat model and guarantees
TLS protects against passive and active network attackers when endpoint validation is correct.

Typical guarantees:

- Confidentiality and integrity in transit.
- Server authentication.
- Forward secrecy with ephemeral key exchange.

Non-goals / residual leakage:

- Some metadata (IP, timing, traffic patterns) may remain visible.

### 25. Why TLS 1.3 took years
Large protocols require:

- Proof-oriented design.
- Adversarial cryptanalysis.
- Standardization trade-offs.
- Interop testing across large ecosystems.
- Implementation hardening at scale.

Strong cryptography without deployability is useless. Deployability without formal discipline is dangerous.

### 26. From hard problems to real-world protection
The path is:

- Hardness assumption -> construction -> proof/model -> protocol -> implementation -> deployment.

Any weak boundary can collapse guarantees. Senior engineering practice is about managing those boundaries explicitly.

### 27. Password manager cryptography (project-style deep dive)
Secure vault design usually includes:

- Master password -> memory-hard KDF -> root key hierarchy.
- Per-record encryption with unique nonces.
- MAC/AEAD for integrity.
- Optional hardware-backed key wrapping.

Threat focus:

- Offline brute-force after database theft.
- Memory exposure and process compromise.
- Backup/recovery design without provider decryption capability.

### 28. Secure messenger architecture essentials
A robust E2EE messenger needs:

- Authenticated key agreement.
- Continuous key evolution (ratcheting).
- Replay and out-of-order handling.
- Multi-device consistency and safe key migration.
- Metadata minimization strategy.

Most real breakages come from identity UX, state sync, backup flows, and metadata channels.

### 29. Formal protocol modeling mindset (ProVerif-style)
Formal methods help verify properties such as:

- Secrecy of session keys.
- Mutual authentication/correspondence.
- Replay resistance.

Key caution:

- Verification proves properties of the model, not necessarily of full implementations.
- Parsing bugs, side channels, and platform assumptions can invalidate "verified" confidence.

### 30. Zero-knowledge game fairness (Battleship pattern)
Pattern:

- Commit to hidden state at game start.
- Prove each response is consistent with committed state.
- Reveal only minimal information per step.

This demonstrates how ZK can enforce fairness and correctness without leaking private strategy/state.

### 31. Post-quantum migration fundamentals
Classical RSA/DH/ECDH assumptions are threatened by large-scale quantum capability.

Migration strategy should include:

- PQ KEM/signature integration.
- Hybrid modes during transition.
- Downgrade protection and algorithm agility.
- Careful performance and bandwidth planning.

### 32. Private contact discovery (PSI/OPRF perspective)
Objective: discover overlap between user contacts and service users without exposing full sets.

Core techniques:

- Private Set Intersection (PSI).
- Oblivious PRFs for scalable private matching.

Design concerns:

- Enumeration abuse prevention.
- Rate limiting and anti-scraping controls.
- Metadata leakage minimization.

### 33. Privacy-preserving age verification
Desired statement: "age >= threshold" without revealing identity or birthdate.

Typical ingredients:

- Anonymous credentials.
- Commitments (e.g., Pedersen-style).
- ZK predicate/range proofs.
- Unlinkability between verification sessions.

The challenge is balancing compliance requirements with anti-surveillance privacy guarantees.

### 34. Time-locked and delayed-reveal cryptography
Goal: prevent early decryption before an objective time/event.

Families of approaches:

- Timelock puzzles (sequential work assumptions).
- Threshold release via distributed randomness/signature networks.

Security targets:

- No early access.
- Public verifiability of release conditions.
- No single trusted escrow authority.

### 35. One-line technical summary
Applied cryptography turns hardness assumptions and formal security models into deployable protocols that provide confidentiality, integrity, authentication, privacy, and verifiable computation under hostile real-world conditions.


# The Challenges of Bringing Cryptography from  Research Papers to Products: Results from an Interview Study with Experts

## Cryptography Productization Notes

**Paper:** *The Challenges of Bringing Cryptography from Research Papers to Products: Results from an Interview Study with Experts*
**Venue:** USENIX Security 2024
**Scope:** The paper studies why cryptographic research often fails to become secure, usable, production ready products. It is based on 21 semi structured interviews with experienced cryptography experts from academia, industry, nonprofit, and governmental organizations. 

---

## 1. Core Idea

Cryptography does not fail only because the mathematics is wrong.

In practice, cryptography often fails because the path from research paper to product is fragmented. A primitive or protocol can be theoretically sound but still become insecure when it passes through standardization, implementation, library API design, product integration, operational deployment, and user adoption.

The paper identifies several root causes:

1. Miscommunication between stakeholders.

2. Unclear responsibilities.

3. Misaligned incentives.

4. Weak or confusing standards.

5. Low quality reference implementations.

6. Poor usability for developers and users.

7. Lack of people who can translate between cryptographic theory and production engineering. 

---

## 2. Main Thesis

The main thesis is:

```text
Cryptographic security is not equal to primitive security.

Cryptographic security =
primitive security
× implementation security
× API safety
× protocol composition
× operational correctness
× usability
× incentive alignment
```

If one part is close to zero, the deployed system can fail.

A secure algorithm is only one component. To become a secure product, it also needs safe APIs, robust implementations, readable standards, clear assumptions, interoperability tests, migration guidance, and usable product behavior.

---

## 3. Cryptography Adoption Path

The paper describes a simplified path for bringing cryptography from research into products:

```text
Cryptographic research
→ algorithm and protocol design
→ cryptanalysis and formal analysis
→ standardization
→ secure implementation in cryptographic libraries
→ product integration
→ adoption by users and organizations
```

The ecosystem map on page 8 shows that this path involves many roles: cryptographic designers, theoretical cryptographers, cryptanalysts, standard development organizations, applied cryptographers, product designers, product security analysts, governments, media, digital rights groups, organizations, and end users. 

## Note

The adoption path is not purely technical. It is a system involving people, incentives, institutions, software engineering constraints, product requirements, legal pressure, usability expectations, and business interests.

---

## 4. Research Code Is Not Product Code

A major problem is that research implementations are often treated as if they were production implementations.

The paper makes it clear that academic code is commonly built to support a paper, demonstrate feasibility, or reproduce benchmarks. It is usually not designed to be safely reused in production systems.

Research code may lack:

1. Constant time guarantees.

2. Side channel resistance.

3. Secure randomness handling.

4. Robust input validation.

5. Memory safety.

6. Clear error handling.

7. Misuse resistant APIs.

8. Safe serialization.

9. Comprehensive test vectors.

10. Fuzzing coverage.

11. Interoperability testing.

12. Secure build and release processes.

13. Long term maintenance.

The paper also notes that academic incentives tend to reward papers, novelty, and performance results more than maintainable engineering artifacts. 

## Note

A proof of concept should never be assumed to be safe for production.

Correct mental model:

```text
research implementation ≠ reference implementation ≠ production implementation
```

A research implementation proves that an idea can work.

A reference implementation should make the specification understandable.

A production implementation must survive real attackers, bad inputs, side channels, compiler behavior, deployment mistakes, platform differences, and long term maintenance pressure.

---

## 5. Academic Incentives Are Misaligned

The paper argues that academic cryptographers are usually rewarded for publishing in strong venues, not for maintaining production quality cryptographic code or participating in long standardization processes.

This creates a structural gap:

```text
The people who design cryptography are not always incentivized to make it deployable.
```

Several problems follow from this:

1. Researchers may optimize for performance benchmarks rather than safe engineering.

2. Practical implementation work may not produce enough academic credit.

3. Standardization work is time consuming but often under rewarded.

4. Secure software maintenance is rarely treated as a high status academic output.

5. Cross disciplinary work between cryptography and software engineering is difficult and under incentivized. 

## Note

If the ecosystem rewards papers more than deployable security, then many strong ideas will remain trapped in papers or will be deployed incorrectly.

For serious adoption, funding bodies and conferences should value:

1. Production ready implementations.

2. Reusable libraries.

3. Verified code.

4. Usable APIs.

5. Documentation.

6. Interoperability suites.

7. Participation in open standards.

8. Collaboration with software engineers.

---

## 6. Standardization Is Necessary but Fragile

Standardization is one of the most important bridges between research and products. However, the paper shows that standards can also become bottlenecks.

Problems include:

1. Standards may be hard to read.

2. Standards may be ambiguous.

3. Different actors may use the same terms differently.

4. Implementers may not be involved early enough.

5. Real user requirements may be misunderstood.

6. Different stakeholders may push for their own interests.

7. Security goals may conflict with business, compliance, or monitoring requirements.

8. Closed standards can exclude independent cryptanalysis.

The paper discusses how open standardization processes such as IETF and NIST competitions are generally viewed more positively than more closed processes, but even open processes can suffer from conflicting incentives and communication failures. 

## Note

A standard is not secure just because it is a standard.

Before trusting a cryptographic standard, ask:

```text
Who designed it?

Who reviewed it?

What threat model does it assume?

What are the explicit security goals?

What are the non goals?

Are downgrade cases specified?

Are invalid inputs specified?

Are failure modes specified?

Are test vectors complete?

Can two independent implementations interoperate?

Was the process open to independent cryptanalysis?

Are implementation requirements clear?

Are operational assumptions documented?
```

---

## 7. Standards Need Better Engineering Usability

The paper highlights that specifications are often written by experts for experts. This creates a serious usability problem for implementers.

A standard may be mathematically correct but still difficult to implement securely if it lacks:

1. Clear structure.

2. Explicit security goals.

3. Executable examples.

4. Complete test vectors.

5. Negative test cases.

6. Clear failure handling.

7. Parameter validation rules.

8. Migration guidance.

9. Version negotiation rules.

10. Implementation notes for common platforms.

11. Guidance on side channel hazards.

12. Guidance on safe randomness and key lifecycle.

The paper’s recommendations include making standards more machine readable, more executable, more accessible, and more strongly tested from an implementer perspective. 

## Note

A good cryptographic standard should behave like an engineering artifact, not only like a mathematical description.

Ideal standard package:

```text
specification
test vectors
negative tests
interoperability tests
reference implementation
security considerations
misuse cases
deployment profile
migration plan
version negotiation rules
formal model where possible
```

---

## 8. Reference Implementations Are Dangerous When Misunderstood

The paper gives major attention to reference implementations. They are useful because they help implementers understand a standard and test interoperability. But they are dangerous when people mistake them for production quality code.

The paper identifies multiple problems:

1. Proof of concept code may be mislabeled as a reference implementation.

2. Optimized implementations may be too complex to understand.

3. Developers may copy code without understanding assumptions.

4. Hard coded values or insecure configurations may propagate into products.

5. Some teams lack cryptographic expertise to judge whether a reference implementation is safe.

6. Low quality reference implementations can seed an ecosystem with bad code. 

## Note

Reference implementations should prioritize clarity, correctness, and interoperability.

Production implementations should prioritize:

1. Constant time behavior.

2. Side channel resistance.

3. Memory safety.

4. Fault resistance.

5. Platform hardening.

6. API safety.

7. Dependency control.

8. Release integrity.

9. Performance only after correctness and security.

Useful labels:

```text
Proof of concept only

Educational example only

Reference implementation for readability

Reference implementation for interoperability

Hardened production candidate

Verified implementation
```

Ambiguous labeling is a security risk.

---

## 9. Communication Gaps Are a Root Cause

The paper repeatedly points to communication gaps between groups.

Important groups include:

1. Theoretical cryptographers.

2. Applied cryptographers.

3. Standards authors.

4. Library maintainers.

5. Software developers.

6. Product security engineers.

7. Product managers.

8. End users.

9. Regulators.

10. Digital rights groups.

The problem is not only that people lack knowledge. The deeper problem is that assumptions are lost while cryptographic ideas move from one group to another.

For example, a paper may assume:

1. Nonces are unique.

2. Randomness is strong.

3. Keys are generated in a trusted environment.

4. Decryption errors are handled safely.

5. Protocol messages are domain separated.

6. Implementations are constant time.

7. The attacker model excludes certain operational compromises.

These assumptions may disappear by the time the system reaches product code. 

## Note

The most dangerous failure mode is:

```text
A developer uses a correct primitive under incorrect assumptions.
```

Examples:

1. AEAD with nonce reuse.

2. Signatures without domain separation.

3. Key exchange without authentication.

4. Password hashing with weak parameters.

5. Encryption without integrity.

6. Ignoring authentication failure.

7. Decrypting before tag verification.

8. Reusing test keys in real deployments.

9. Assuming forward secrecy where it does not exist.

10. Deploying post quantum cryptography without a migration and hybrid strategy.

---

## 10. Cryptographic Artifacts Need Assumption Manifests

One practical engineering response is to attach an assumption manifest to every cryptographic design, library, or protocol.

Example:

```json
{
  "security_goals": [
    "confidentiality",
    "integrity",
    "authenticity",
    "forward secrecy"
  ],
  "assumptions": [
    "nonces are unique for each key",
    "random number generation is cryptographically secure",
    "private keys are generated on trusted devices",
    "protocol transcript is domain separated",
    "authentication failure stops processing immediately"
  ],
  "misuse_cases": [
    "do not reuse a nonce with the same key",
    "do not ignore authentication failure",
    "do not expose plaintext before verification",
    "do not allow downgrade to obsolete algorithms"
  ]
}
```

## Note

Assumptions should be treated as part of the API contract.

If an implementation depends on a condition, the system should either enforce it or make violation extremely difficult.

---

## 11. Developer Usability Is Cryptographic Security

The paper treats usability broadly. Usability is not only about end users. It also applies to cryptographic libraries, APIs, standards, documentation, and reference implementations.

Developer usability failures cause real vulnerabilities.

Dangerous API patterns:

1. APIs that require manual nonce management without strong guardrails.

2. APIs that expose raw primitives without safe composition.

3. Optional authentication.

4. Manual padding selection.

5. Manual curve or parameter selection.

6. Boolean verification results without strong error semantics.

7. Raw key material passed everywhere.

8. Insecure algorithms kept as easy options.

9. Examples that show unsafe patterns.

10. Documentation that hides critical assumptions. 

Safer API patterns:

1. AEAD by default.

2. Opaque key types.

3. Typed nonces.

4. Domain separated signing contexts.

5. Safe defaults.

6. No insecure algorithm options in default paths.

7. Clear key lifecycle APIs.

8. Fail closed behavior.

9. High level protocol APIs instead of raw primitives.

10. Misuse resistant construction where possible.

## Note

A cryptographic library should make the secure path the easiest path.

Good API design removes unnecessary decisions from developers.

---

## 12. Product Adoption Requires Preserving User Value

The paper explains that users often reject cryptographic systems when security removes features they care about.

Examples include:

1. Search.

2. Backups.

3. Account recovery.

4. Spam filtering.

5. Multi device synchronization.

6. AI assisted processing.

7. Easy sharing.

8. Enterprise visibility and compliance workflows.

For example, encrypted email has struggled partly because key management and feature loss create friction. Users often do not want encryption as an abstract property. They want a product that works, protects them, and does not make their workflow worse. 

## Note

Security that destroys product value will be bypassed.

Successful cryptographic adoption usually has these properties:

1. Secure by default.

2. Minimal user decision making.

3. No visible key management burden.

4. Clear recovery model.

5. Usable multi device support.

6. Safe migration path.

7. No major performance penalty.

8. No unnecessary feature loss.

9. Clear failure states.

10. Strong integration into existing workflows.

---

## 13. Industry Incentives Can Conflict With Security

Industry actors may participate in standards and cryptographic design for legitimate reasons such as interoperability, compliance, and product security.

But the paper also shows that industry incentives can conflict with stronger cryptographic outcomes.

Possible conflicts:

1. Companies may prefer backward compatibility over stronger security.

2. Companies may resist changes that require infrastructure investment.

3. Vendors may push their own protocols for commercial advantage.

4. Organizations may want visibility into encrypted traffic for monitoring or compliance.

5. Product teams may prioritize usability and features over cryptographic rigor.

6. Cost reduction may dominate long term security.

## Note

When evaluating an industry backed cryptographic design, inspect incentives.

Ask:

```text
Does this design improve user security?

Does it mainly preserve legacy infrastructure?

Does it create vendor lock in?

Does it weaken forward secrecy?

Does it add exceptional access?

Does it increase implementation complexity?

Does it make secure deployment easier or harder?
```

---

## 14. Open Standards Matter

The paper recommends stronger support for open standardization and warns that closed or expensive standards can exclude researchers, independent cryptanalysts, and implementers.

Open processes improve security because they allow:

1. Broader review.

2. Independent cryptanalysis.

3. Public criticism.

4. More implementer feedback.

5. Better trust.

6. More transparent competition requirements.

7. Earlier detection of bad assumptions. 

## Note

Cryptography should be reviewed in public whenever possible.

A design that cannot survive public expert review should not become critical infrastructure.

---

## 15. Need for Translator Roles

One of the most important observations in the paper is the shortage of people who can act as translators between theory and practice.

These people understand enough cryptographic theory to respect security assumptions, and enough software engineering to build robust systems.

They can translate between:

1. Proof assumptions and implementation requirements.

2. Standard language and developer tasks.

3. Cryptographic goals and product requirements.

4. Research code and production libraries.

5. Security properties and user visible behavior.

The paper suggests that this translator role is essential but often poorly rewarded. 

## Note

In a mature organization, cryptographic adoption should involve a dedicated bridge role.

This role should review:

1. Protocol assumptions.

2. API design.

3. Library selection.

4. Key management.

5. Randomness.

6. Side channel exposure.

7. Error handling.

8. Upgrade paths.

9. Interoperability.

10. Operational deployment.

11. Developer documentation.

12. Incident response and migration planning.

## 17. Recommendations for Academia

The paper recommends improving incentives and collaboration across the cryptography ecosystem.

For academia:

1. Reward production quality implementations.

2. Reward participation in standardization.

3. Treat usable reference implementations as valuable research output.

4. Encourage collaboration with software engineering experts.

5. Improve communication across cryptography subfields.

6. Make assumptions clearer in papers and artifacts.

7. Avoid labeling proof of concept code as reference implementation.

8. Include documentation and test vectors with research artifacts. 

## Note

Academic cryptography should not stop doing theoretical research. But when a result is intended for real adoption, the artifact must be packaged for engineering use.

---

## 18. Recommendations for Industry

For industry:

1. Invest in core cryptographic infrastructure.

2. Participate in open standard development.

3. Communicate implementation problems upstream.

4. Avoid private cryptographic designs unless absolutely necessary.

5. Prefer established and reviewed primitives.

6. Fund maintenance of critical open source libraries.

7. Use product security review before deployment.

8. Design cryptographic features so users are not forced to choose between security and usability. 

## Note

The biggest security gains often come when widely used products adopt transparent security by default.

---

## 19. Recommendations for Standardization Organizations

For standardization organizations:

1. Make standards easier to read.

2. Make standards easier to implement.

3. Include test vectors.

4. Include negative tests.

5. Make specifications machine readable where possible.

6. Make specifications executable where possible.

7. Include implementers early.

8. Include academics early.

9. Include product and usability experts early.

10. Perform requirement analysis before drafting.

11. Prefer open processes.

12. Make participation easier for independent researchers. 

## Note

A standard should be tested not only for mathematical correctness, but also for implementability.

---

## 20. Final Note

The paper’s strongest lesson is that cryptography adoption is an engineering ecosystem problem.

A cryptographic system becomes product ready only after it survives:

```text
cryptanalysis
formal review
standardization review
implementation review
API misuse review
side channel review
interoperability testing
developer usability testing
deployment review
migration review
operational review
```

A secure primitive is necessary, but it is not sufficient.

The real objective is not to publish cryptography.

The real objective is to deliver cryptography that can be safely implemented, safely integrated, safely operated, and safely used.
