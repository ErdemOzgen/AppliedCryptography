# Notes

File inspected: Applied Cryptography, Summer 2026, Part 1: Provable Security, 1.7: Hard Problems and Diffie Hellman. 

## 1. Main idea of the lecture

This file explains why modern cryptography works at all. The core claim is:

Cryptographic systems are built by reducing security to computational problems that are believed to be infeasible to solve.

That means cryptography rarely proves that an attacker can never break a system. Instead, it proves statements like:

```text
If an attacker can break this protocol efficiently,
then the attacker can also solve this hard mathematical problem efficiently.
```

So the security of the protocol rests on the assumed hardness of the underlying problem.

The lecture focuses mainly on:

• Hard computational problems
• Complexity theory
• Discrete logarithms
• Diffie Hellman key exchange
• Real deployment issues
• Attacks on Diffie Hellman
• Authenticated key exchange
• The transition to elliptic curves and post quantum key exchange
• A short RSA overview

## 2. Security goals

The file starts by grounding cryptography in three major goals.

Confidentiality means only intended parties can read the data. Example: a private Signal message should only be readable by sender and recipient.

Authentication means the receiver can verify who sent the data. Example: if a server receives a message from a client, it should know whether that client actually sent it.

Integrity means unauthorized modification can be detected. Example: a software update should fail verification if an attacker modifies the download.

The lecture also mentions TLS, FileVault, and Signal as real systems combining these goals. TLS gives confidentiality and authentication for web connections. FileVault protects stored data. Signal adds advanced properties such as post compromise security.

## 3. Why access control alone is insufficient

The file asks why we need cryptography if we already have usernames, passwords, server checks, and access control.

The answer is that traditional access control assumes too much trust in the server and the network.

Access control alone does not solve:

• Protection during transmission
• Verification of integrity
• Trust establishment between strangers
• Secure communication over hostile networks
• Protection from malicious intermediaries

Cryptography gives stronger tools. It lets two parties communicate securely even when the channel is observable or partially hostile.

## 4. The “actual magic” idea

The key motivating problem is:

Can Alice and Bob agree on a secret while an eavesdropper sees every message they exchange?

Diffie Hellman says yes.

The visual on page 9 shows the classic exchange:

```text
Alice sends g^a mod p
Bob sends g^b mod p
Alice computes (g^b)^a mod p
Bob computes (g^a)^b mod p
Both get g^(ab) mod p
```

An eavesdropper sees:

```text
g, p, g^a mod p, g^b mod p
```

but should not be able to compute:

```text
g^(ab) mod p
```

This is the central magic of the lecture.

## 5. Hard problems

A hard problem is a computational problem for which no efficient algorithm is known.

In cryptography, hard problems are used to create asymmetry:

```text
Easy for honest parties
Hard for attackers
```

Example:

```text
Easy: compute g^x mod p
Hard: given g, p, and g^x mod p, recover x
```

This is the discrete logarithm problem.

The lecture stresses that “believed hard” does not mean “proven impossible.” It means decades of research have not found an efficient classical algorithm under proper parameter choices.

## 6. Discrete logarithm problem

The discrete logarithm problem is defined as:

```text
Given g, p, and h = g^x mod p,
find x.
```

For small numbers, this is easy by trial.

Example:

```text
2^3 mod 17 = 8
```

Given `g = 2`, `p = 17`, and `h = 8`, the answer is `x = 3`.

For cryptographic size groups, such as 2048 bit finite field groups or 256 bit elliptic curve groups, the problem is believed infeasible for classical computers.

Important nuance:

The forward direction is efficient because modular exponentiation can be done quickly using square and multiply style algorithms.

The reverse direction is hard because there is no known efficient classical method to recover the exponent in properly chosen groups.

## 7. Asymmetric and symmetric primitives

The file contrasts asymmetric and symmetric cryptography.

Asymmetric primitives include Diffie Hellman, RSA, ML KEM, ECDSA, EdDSA, and related systems. They use public and private values and usually depend on algebraic hardness assumptions.

Symmetric primitives include AES, SHA 2, ChaCha20, and HMAC. They usually rely less on algebraic hardness and more on resistance to cryptanalysis, design arguments, and security models such as the random oracle model.

A good way to summarize the distinction:

```text
Asymmetric cryptography:
security from structured mathematical hardness.

Symmetric cryptography:
security from carefully designed unstructured transformations.
```

## 8. Complexity theory foundation

The lecture introduces computational complexity because cryptographic security depends on how attack cost grows as input size grows.

The graph on page 16 illustrates the practical difference between linear, quadratic, and exponential growth. Linear and polynomial growth may remain manageable. Exponential growth quickly becomes infeasible.

Common complexity examples:

```text
O(n)       linear
O(n^2)     quadratic
O(2^n)     exponential
```

Cryptography tries to choose parameters so that the best known attack requires infeasible work, often exponential or subexponential work with enormous constants.

## 9. Computational problems

The file separates computational problems into decision problems and search problems.

A decision problem has a yes or no answer.

Example:

```text
Is 217 prime?
```

A search problem asks for a value.

Example:

```text
Find x such that g^x = h mod p.
```

Cryptographic attackers often face search problems, such as recovering a key, finding a preimage, or computing a shared secret.

Complexity theory often studies decision problems because they are easier to classify formally.

## 10. Class P

Class P contains problems solvable in polynomial time.

```text
P = TIME(n) union TIME(n^2) union TIME(n^3) ...
```

In practice, P is treated as the class of efficiently solvable problems.

Examples:

• Sorting
• Searching
• Basic arithmetic
• Modular exponentiation

Cryptography usually wants legitimate operations in P, while attack operations should not be feasible at selected security parameters.

## 11. Space complexity

The file also discusses memory usage.

```text
SPACE(f(n)) = problems solvable using O(f(n)) memory
```

Important relationship:

```text
TIME(f(n)) is contained in SPACE(f(n))
```

The intuition is that an algorithm cannot write more memory cells than the number of steps it executes.

However, low memory does not imply fast execution. Brute force key search may use little memory but still take astronomical time.

This matters because modern cryptography often cares about both time and memory, especially in password hashing and memory intensive key derivation.

## 12. Class NP

NP contains decision problems where a proposed solution can be verified in polynomial time.

The key intuition:

```text
A solution may be hard to find,
but easy to check.
```

Cryptographic examples from the file:

Hash preimage style decision problem:

```text
Given H, does there exist M such that hash(M) = H?
```

If someone gives candidate `M0`, verification is easy:

```text
Compute hash(M0)
Check whether it equals H
```

Key recovery style decision problem:

```text
Given plaintext P and ciphertext C,
does there exist key K such that C = E(K, P)?
```

If someone gives candidate `K0`, verification is easy:

```text
Encrypt P with K0
Check whether result equals C
```

So these are in NP as decision formulations.

## 13. What is not naturally in NP

The lecture notes that some attack settings are not naturally expressible as NP problems.

For example, in a known ciphertext only scenario, the attacker may have ciphertexts but not corresponding plaintexts. If someone gives a candidate key, the verifier may not know whether the decrypted outputs are correct.

Also, proving no solution exists is generally harder than verifying a provided solution. This relates to complement classes such as co NP, although the file does not go deep into that.

## 14. NP complete problems

NP complete problems are the hardest problems in NP.

They have two properties:

• They are in NP
• Every problem in NP can be reduced to them in polynomial time

Examples in the file:

• Boolean satisfiability
• Traveling salesman decision variants
• Graph coloring
• Subset sum
• Generalized Sudoku style problems

The surprising point is that these problems can look completely unrelated but are computationally equivalent through reductions.

## 15. Reductions

A reduction transforms one problem into another efficiently while preserving the answer.

If problem A reduces to problem B, then an efficient solver for B gives an efficient solver for A.

This is central to cryptographic proofs.

A typical cryptographic proof shape is:

```text
Assume attacker breaks protocol.
Use that attacker to solve hard problem.
But hard problem is assumed infeasible.
Therefore attacker should not exist.
```

This is not absolute proof. It is conditional proof.

## 16. P versus NP

The lecture discusses the famous open question:

```text
Does P = NP?
```

Meaning:

```text
If a solution can be verified efficiently,
can it also be found efficiently?
```

Most researchers believe:

```text
P is not equal to NP
```

but nobody has proven it.

The file presents the cryptographic apocalypse scenario: if P equals NP in a constructive and practical way, many cryptographic assumptions could collapse. Key recovery, preimage search, and many other attack problems could become efficient.

Important nuance:

Even if P equals NP mathematically, the polynomial algorithm might still be impractical. For example, `n^1000` is polynomial but useless in practice. Cryptographic disaster would require practical efficient algorithms, not only a theoretical equality.

## 17. Why NP complete problems are not directly enough for cryptography

This is one of the most important conceptual points in the file.

NP complete means hard in the worst case.

Cryptography needs average case hardness.

Worst case hardness says:

```text
Some instances are hard.
```

Average case hardness says:

```text
Randomly generated instances are usually hard.
```

Cryptographic keys, primes, exponents, and public values are generated randomly or pseudorandomly. Therefore security requires that typical generated instances are hard, not merely that some pathological instance is hard.

This is why practical cryptography usually uses problems like:

• Integer factorization
• Discrete logarithm
• Lattice problems

These are believed hard on average for appropriate distributions, even though they are not known to be NP complete.

## 18. Average case hardness and cryptography

The file contrasts worst case and average case directly.

Worst case hardness:

```text
Some inputs are very hard.
Some inputs may be trivial.
```

Average case hardness:

```text
Random valid inputs are hard with high probability.
```

Cryptography needs the second.

For Diffie Hellman, the attacker sees something like:

```text
g, g^a mod p, g^b mod p
```

and should not recover:

```text
a, b, or g^(ab) mod p
```

for random secret exponents.

For RSA, the attacker sees:

```text
n = p q
```

and should not recover:

```text
p and q
```

when `p` and `q` are generated correctly.

## 19. Mathematical groups

Diffie Hellman operates inside a mathematical group.

A group is a set with an operation satisfying four properties:

• Closure
• Identity
• Inverses
• Associativity

For finite field Diffie Hellman, the group is often:

```text
Z_p^*
```

which means the nonzero integers modulo a prime `p`, with multiplication modulo `p`.

Example:

```text
Z_5^* = {1, 2, 3, 4}
```

Operations stay inside the group:

```text
3 x 4 = 12 mod 5 = 2
```

The group structure ensures that exponentiation, inversion, and shared secret computation behave predictably.

## 20. Generators

A generator is an element whose powers cover the group or a chosen subgroup.

Example from the lecture:

```text
In Z_5^*, choose g = 2

2^1 mod 5 = 2
2^2 mod 5 = 4
2^3 mod 5 = 3
2^4 mod 5 = 1
```

The powers produce every element:

```text
{1, 2, 3, 4}
```

So `2` is a generator of `Z_5^*`.

Generator choice matters. Poor generator or subgroup selection can create catastrophic vulnerabilities, as later shown in the Logjam findings.

## 21. Diffie Hellman key exchange

The mathematical version:

Public setup:

```text
p = large prime
g = generator
```

Alice:

```text
Choose secret a
Compute A = g^a mod p
Send A
```

Bob:

```text
Choose secret b
Compute B = g^b mod p
Send B
```

Alice computes:

```text
S = B^a mod p = (g^b)^a mod p = g^(ab) mod p
```

Bob computes:

```text
S = A^b mod p = (g^a)^b mod p = g^(ab) mod p
```

Both arrive at the same shared secret without sending it.

## 22. Small Diffie Hellman example

The file gives a toy example:

```text
p = 13
g = 2
a = 5
b = 7
```

Alice computes:

```text
A = 2^5 mod 13 = 6
```

Bob computes:

```text
B = 2^7 mod 13 = 11
```

Alice computes:

```text
S = 11^5 mod 13 = 7
```

Bob computes:

```text
S = 6^7 mod 13 = 7
```

Shared secret:

```text
S = 7
```

This example is intentionally insecure because the numbers are tiny. In practice, parameters must be large enough to resist discrete logarithm attacks.

## 23. Discrete logarithm problem versus Diffie Hellman problems

The file distinguishes three related assumptions.

Discrete logarithm problem:

```text
Given g and g^a, recover a.
```

Computational Diffie Hellman:

```text
Given g^a and g^b, compute g^(ab).
```

Decisional Diffie Hellman:

```text
Given g^a, g^b, and X,
decide whether X = g^(ab) or X is random.
```

The hierarchy in the file:

```text
DDH is no harder than CDH
CDH is no harder than DLP
```

In notation:

```text
DDH <= CDH <= DLP
```

Interpretation:

If you can solve DLP, you can solve CDH.

If you can solve CDH, you can solve DDH.

But the reverse directions are not generally known.

## 24. Why CDH matters

CDH captures the passive eavesdropper problem.

An attacker sees:

```text
g^a mod p
g^b mod p
```

The attacker wants:

```text
g^(ab) mod p
```

without knowing `a` or `b`.

This is exactly the attack target in unauthenticated passive Diffie Hellman.

If CDH is hard in the chosen group, a passive observer should not compute the shared secret.

## 25. Why DDH matters

DDH is about indistinguishability.

Even if an attacker cannot compute the full shared secret, they should not be able to distinguish it from random or learn partial information.

This matters because cryptographic protocols often require the shared secret to behave like high entropy random input to a key derivation function.

DDH supports stronger security proofs for constructions such as ElGamal encryption and authenticated key exchange protocols.

Important file nuance:

DDH is not hard in every group. In some finite field groups, DDH can be attacked using the Legendre symbol and quadratic residuosity leakage. This is one reason modern systems often prefer elliptic curve groups where DDH style assumptions are believed to hold more cleanly.

## 26. Real world Diffie Hellman

The file lists several major uses:

• TLS and HTTPS
• Signal
• SSH
• VPNs

Modern variants include elliptic curve Diffie Hellman and post quantum key exchange algorithms.

In practice, Diffie Hellman is not usually used alone. It is embedded inside a larger protocol that handles identity, transcript binding, key derivation, downgrade resistance, and algorithm negotiation.

## 27. TLS handshake with Diffie Hellman

The simplified TLS flow in the file:

1. Client says it wants a secure connection.
2. Server sends certificate and Diffie Hellman parameters or key share.
3. Client sends its own Diffie Hellman public value.
4. Both sides compute the shared secret.
5. A key derivation function derives traffic keys.
6. Later communication is encrypted.

Important correction for modern TLS:

TLS 1.3 does not work exactly like older finite field Diffie Hellman handshakes. It commonly uses ephemeral elliptic curve key shares such as X25519, and the certificate authenticates the server transcript rather than merely being a container for static DH parameters. But the conceptual point in the file is correct: Diffie Hellman establishes shared secret material, and authentication prevents active substitution.

## 28. Signal and repeated Diffie Hellman

The file mentions Signal’s X3DH and Double Ratchet.

X3DH performs an asynchronous initial authenticated key agreement, allowing a sender to start a secure session even when the recipient is offline.

The Double Ratchet then repeatedly updates keys. It uses symmetric ratcheting and Diffie Hellman ratcheting to provide strong properties:

• Forward secrecy
• Post compromise security
• Recovery after temporary compromise
• Continuous key evolution

The visual on page 80 shows Signal safety number verification. This is an out of band authentication mechanism using fingerprints derived from identity keys.

## 29. Logjam findings

The Logjam section is a major deployment lesson.

The file identifies three categories of real weakness:

• 512 bit primes still used
• Composite order subgroup attacks
• Misconfigured DSA groups

The important message:

Correct mathematics does not save incorrect deployments.

A protocol can be theoretically sound while real systems fail because of weak parameters, bad defaults, small groups, legacy export cryptography, or missing validation.

## 30. 512 bit Diffie Hellman primes

The file says researchers found browser trusted servers using 512 bit primes.

This is disastrous because 512 bit finite field discrete logarithms are within reach of serious attackers.

A passive attacker can record traffic and later compute discrete logarithms if the group is weak or precomputed.

The file mentions test decryption involving `www.fbi.gov`, which used a weak OpenSSL default group until 2015.

Lesson:

```text
Default parameters are security critical.
Administrators often do not change defaults.
Therefore library defaults must be safe.
```

## 31. Composite order subgroup attacks

The file also discusses unsafe primes and subgroup problems.

If `p - 1` has small factors, then the multiplicative group contains small subgroups. If the generator or peer public value is not validated correctly, an attacker can force computations into a weak subgroup and recover information about the secret exponent.

Important nuance from the file:

A non safe prime is not automatically fatal if the generator is chosen correctly and subgroup handling is sound. The failure occurs when unsafe group structure combines with poor generator choice, short exponents, or missing public key validation.

Operational guidance:

• Use standardized safe groups
• Validate peer public values
• Avoid custom finite field groups
• Avoid short exponents unless the protocol and group are designed for them
• Prefer modern elliptic curve groups with safer APIs

## 32. Unauthenticated Diffie Hellman

The file emphasizes that plain Diffie Hellman does not authenticate identities.

It protects against passive eavesdropping, not active manipulation.

The attack:

Mallory sits between Alice and Bob.

Alice thinks she exchanges with Bob, but actually exchanges with Mallory.

Bob thinks he exchanges with Alice, but actually exchanges with Mallory.

Result:

```text
Alice shares key with Mallory.
Bob shares key with Mallory.
Alice and Bob do not share a key with each other.
```

Mallory can decrypt, modify, and reencrypt traffic.

## 33. Man in the middle attack flow

The file gives this flow:

```text
Alice sends g^a
Mallory replaces it with g^m to Bob

Bob sends g^b
Mallory replaces it with g^m to Alice
```

Then:

```text
Alice computes g^(am)
Bob computes g^(bm)
Mallory knows both
```

So Mallory becomes a live translation layer between both sides.

The critical reason this works:

```text
Diffie Hellman public values do not carry identity by themselves.
```

They look like random group elements. Alice cannot tell whether a value came from Bob or Mallory.

## 34. Authenticated key exchange

The solution is authenticated key exchange.

An authenticated key exchange protocol does two things:

• Establishes shared secret material
• Authenticates the party or parties involved

Common methods from the file:

• Digital signatures
• Certificates
• Existing shared secrets
• Password based authenticated protocols

The practical rule:

```text
Never use raw Diffie Hellman as a complete secure channel protocol.
Use a vetted authenticated key exchange protocol.
```

Examples:

• TLS 1.3
• Noise protocol framework patterns
• Signal X3DH
• SSH key exchange with host key authentication
• IKE for IPsec

## 35. TLS authentication

The file explains how HTTPS prevents active substitution.

The server provides a certificate. The client checks:

• Is the certificate signature valid?
• Is the issuing authority trusted?
• Does the certificate match the domain?
• Is the certificate expired?
• Has it been revoked or otherwise rejected by policy?

If checks pass, the browser accepts that the server identity is bound to the key exchange transcript.

If checks fail, the browser warns the user.

Important nuance:

Certificates do not make man in the middle attacks impossible. They make them much harder by requiring compromise of a certificate authority, a local trust store, endpoint device, DNS plus certificate issuance path, or user behavior.

## 36. Signal authentication

Signal does not rely on traditional certificate authorities for user identity.

Instead, it uses long term identity keys and displays safety numbers.

Users can compare these numbers out of band:

• In person
• Over a phone call
• Through another trusted channel

This solves the bootstrapping problem differently from TLS. It is decentralized from a user trust perspective but depends on users actually verifying fingerprints when strong authentication is required.

## 37. SSH authentication

SSH uses host keys.

On first connection, the client sees a host key fingerprint. In theory, the user should verify it out of band.

In practice, many users accept it.

SSH then stores the host key in:

```text
~/.ssh/known_hosts
```

On later connections, if the host key changes, SSH warns loudly.

This model is called trust on first use.

Strength:

• Simple
• Works without public certificate authorities
• Effective after the first clean connection

Weakness:

• Vulnerable on the first connection
• Users often ignore verification
• Key rotation creates operational friction

## 38. Traditional Diffie Hellman versus elliptic curve Diffie Hellman

The file compares finite field Diffie Hellman and elliptic curve Diffie Hellman.

Traditional finite field Diffie Hellman:

• Uses integers modulo `p`
• Requires large values such as 2048 bits or more
• Slower
• Larger public values

Elliptic curve Diffie Hellman:

• Uses elliptic curve groups
• Achieves comparable security with much smaller keys
• Faster
• Lower bandwidth
• Better for mobile and embedded systems

Examples from the file:

• P 256
• P 384
• X25519
• X448

The practical modern default is often X25519 because it has strong performance and safer implementation properties.

## 39. Quantum threat

The file correctly states that Shor’s algorithm breaks both finite field Diffie Hellman and elliptic curve Diffie Hellman on a sufficiently capable quantum computer.

That means all classical discrete logarithm based key exchange is vulnerable in the long term.

The threat model mentioned is:

```text
Harvest now, decrypt later.
```

An adversary records encrypted traffic today and decrypts it later when quantum capability becomes available.

This matters most for data requiring long term confidentiality.

## 40. Post quantum alternatives

The file mentions several post quantum directions:

• ML KEM based on lattice problems
• Code based alternatives
• Hash based alternatives
• Isogeny based approaches

It also notes that SIDH and SIKE were broken. This is a major lesson: new mathematical assumptions require intense cryptanalysis before deployment confidence is justified.

For current practical key establishment, ML KEM is the most important standardized post quantum key encapsulation mechanism.

A likely future architecture is hybrid key exchange:

```text
Classical ECDH shared secret
plus
Post quantum KEM shared secret
then
Key derivation combines both
```

This protects against both unexpected post quantum weakness and future quantum attacks on elliptic curves.

## 41. RSA overview

The file gives a short RSA section.

RSA was introduced after Diffie Hellman and is based on integer factorization.

Key generation:

```text
Choose large primes p and q
Compute n = p q
Compute phi(n) = (p - 1)(q - 1)
Choose public exponent e
Compute private exponent d such that e d = 1 mod phi(n)
```

Encryption:

```text
c = m^e mod n
```

Decryption:

```text
m = c^d mod n
```

The security assumption is that factoring `n` into `p` and `q` is computationally infeasible. 

## 42. RSA dual functionality

RSA historically mattered because it supported both encryption and digital signatures.

Encryption mode:

• Public key encrypts
• Private key decrypts
• Provides confidentiality

Signature mode:

• Private key signs
• Public key verifies
• Provides authenticity

This dual functionality made RSA enormously influential in TLS, email encryption, SSH, code signing, and certificate infrastructure. 

## 43. RSA in practice

The file notes that RSA dominated for decades.

Common uses:

• HTTPS certificates
• PGP and GPG email encryption
• Software signing
• SSH keys

Key size guidance from the file:

• 1024 bit RSA is deprecated and insecure
• 2048 bit RSA is a current minimum but aging
• 4096 bit RSA is stronger but slower and bulky
• 256 bit elliptic curve keys can give security comparable to roughly 3072 bit RSA

The operational direction is clear: RSA is legacy in many modern protocol designs. 

## 44. Important RSA implementation warning

Raw textbook RSA is not secure.

The formulas:

```text
c = m^e mod n
m = c^d mod n
```

are mathematical primitives, not complete encryption schemes.

Real RSA encryption needs secure padding such as OAEP.

Real RSA signatures need secure padding such as PSS.

Without correct padding, RSA is vulnerable to many attacks, including chosen ciphertext attacks, padding oracle attacks, signature forgery patterns, and subtle encoding failures.

The file mentions implementation pitfalls such as padding oracle attacks and timing attacks as part of why RSA is not covered deeply. 

## 45. Why the lecture does not focus deeply on RSA

The file calls RSA a cryptographic dinosaur.

Main reasons:

• It is being replaced in many systems
• TLS 1.3 prefers modern elliptic curve based signatures and key exchange
• RSA is slower than elliptic curve alternatives
• It has many implementation pitfalls
• Its design pattern does not generalize as well to modern protocols as Diffie Hellman does
• The future focus is elliptic curves and post quantum cryptography

The lecture’s prioritization makes sense: Diffie Hellman ideas survive in ECDH, X25519, Signal, TLS 1.3, Noise style protocols, and post quantum hybrid key exchange. RSA is historically important but less central to modern protocol design.

## 46. Practical engineering guidance from the file

For Diffie Hellman:

• Do not design your own groups
• Use standardized groups or modern curves
• Prefer X25519 or approved elliptic curve groups where appropriate
• Validate public values where the protocol requires it
• Never use unauthenticated Diffie Hellman alone
• Bind key exchange to identities and protocol transcripts
• Use key derivation functions before deriving encryption keys
• Use ephemeral secrets for forward secrecy

For TLS:

• Prefer TLS 1.3
• Disable obsolete finite field groups
• Disable export grade and weak legacy parameters
• Prefer modern cipher suites
• Ensure certificate validation is strict

For SSH:

• Verify host fingerprints for high value systems
• Monitor known host changes
• Prefer modern key types where supported
• Treat first connection as a trust establishment event

For post quantum readiness:

• Identify data needing long term confidentiality
• Track ML KEM adoption
• Prefer hybrid key exchange during transition periods
• Design protocol agility carefully to avoid downgrade attacks

## 47. Key conceptual takeaways

The most important lessons are:

Cryptography is based on hardness assumptions, not magic.

Worst case hardness is not enough. Cryptography needs average case hardness.

Diffie Hellman solves passive key agreement but does not solve authentication.

Authenticated key exchange is the real deployed primitive.

Parameter selection is security critical.

Weak groups, short exponents, bad defaults, and missing validation can destroy a correct algorithm.

Elliptic curve Diffie Hellman is the modern classical form of Diffie Hellman.

Quantum computers threaten all discrete logarithm based Diffie Hellman variants.

Post quantum key exchange is the long term replacement path.

RSA is historically essential but increasingly legacy.

# Notes

## 1. High level map

These readings connect three themes: public key cryptography, computational hardness, and quantum attacks. Diffie and Hellman introduce the idea that parties can coordinate secrets over public channels using computational asymmetry. The Nintendo and Mario hardness works explain how reachability in generalized game worlds can encode hard decision problems. Childs explains why the discrete logarithm problem, which supports classical Diffie Hellman style security, becomes efficiently solvable on a quantum computer through the hidden subgroup problem framework. 

```text
Shared idea

easy forward computation
→ hard inverse or search problem
→ cryptographic security or complexity lower bound
→ quantum algorithms can change the hardness landscape
```

## 2. New Directions in Cryptography

This paper is foundational because it reframes cryptography from secret algorithms and pre shared keys into public algorithms with computational security. Diffie and Hellman argue that traditional cryptography required communicating parties to share a secret key in advance, usually through a secure physical channel, which becomes impractical for large communication networks. 

The key innovation is public key thinking. In a public key cryptosystem, encryption and decryption use distinct keys. The encryption key can be public, while deriving the decryption key from it should be computationally infeasible. This lets anyone send an encrypted message to a recipient without first sharing a secret key with that recipient. 

The paper separates public key encryption from public key distribution. Public key encryption lets anyone encrypt directly to a public key. Public key distribution lets two users communicate over an insecure channel and arrive at a shared secret key, while an eavesdropper should find the shared key computationally infeasible to compute. 

## 3. Diffie Hellman key exchange

The paper proposes a public key distribution method based on the apparent difficulty of discrete logarithms over a finite field. Computing an exponentiation modulo a prime is efficient, but computing the exponent from the result is assumed difficult for carefully chosen parameters. 

Conceptually:

```text
Public parameters

prime q
generator alpha

Alice secret x
Alice public value alpha^x mod q

Bob secret y
Bob public value alpha^y mod q

Shared key
alpha^(xy) mod q
```

Alice computes the shared key by raising Bob’s public value to Alice’s secret exponent. Bob computes the same key by raising Alice’s public value to Bob’s secret exponent. An eavesdropper sees both public values, but should not be able to compute the shared value without solving a discrete logarithm style problem. 

The paper is careful about the proof status. It says that if logarithms modulo q can be computed efficiently, the system is broken, but it does not prove the converse that hardness of discrete logarithms alone guarantees security of the shared key. This distinction is very modern: breaking Diffie Hellman key exchange is related to, but not identical to, solving discrete logarithms in all formulations. 

## 4. One way functions and authentication

Diffie and Hellman also discuss one way functions: functions that are easy to compute but computationally infeasible to invert for almost all outputs. They emphasize that this is not ordinary mathematical noninvertibility. The issue is not that multiple inputs map to one output; the issue is that finding any valid preimage should be computationally infeasible. 

They connect this to password storage. Instead of storing a password directly, a system stores f password. During login, it computes f candidate and compares. If the password file is stolen, the attacker should not be able to recover the original password from the stored image. This idea is recognizable today in password hashing, although modern systems add salts, memory hard functions, rate limits, and migration policies. 

They also identify the need for digital signatures: something easy for anyone to verify but infeasible for anyone except the signer to produce. The paper describes this as a digital equivalent of a written signature and ties it to authentication, contracts, and billing. 

## 5. Practical cryptographic lessons from Diffie Hellman

The paper gives the conceptual birth of public key cryptography, but production deployment needs additional machinery. Plain Diffie Hellman without authentication is vulnerable to man in the middle attacks because the attacker can replace public values. Real protocols therefore authenticate the exchange using signatures, certificates, password authenticated key exchange, or pre shared authentication.

The paper’s finite field version also requires careful group selection. Modern finite field Diffie Hellman must avoid small subgroup attacks, weak primes, reused unsafe parameters, and insufficient exponent entropy. Elliptic curve Diffie Hellman changes the group but keeps the same conceptual structure: public scalar multiplication is easy, recovering the scalar is assumed hard.

## 6. Classic Nintendo Games are Computationally Hard

This paper analyzes generalized versions of major Nintendo game franchises as decision problems. The core question is reachability: given a stage or dungeon, can the player reach the goal from the start? The authors prove NP hardness for generalized versions of Mario, Donkey Kong, Zelda, Metroid, and Pokémon, and PSPACE completeness for Donkey Kong Country games and several Zelda games. ([arXiv][1])

The word generalized is essential. The claim is not that a commercial cartridge level is hard in the complexity theoretic sense. The claim is that if the game mechanics are kept fixed but level size is allowed to grow, then deciding reachability can become computationally hard. ([ar5iv][2])

The main NP hardness framework reduces from 3 SAT. The level is built from gadgets: variable gadgets force a truth assignment choice, clause gadgets are unlocked when a satisfying literal path is visited, and crossover gadgets let paths geometrically cross without letting the player switch paths. The player reaches the finish if and only if the encoded formula is satisfiable. ([ar5iv][2])

```text
3 SAT formula
→ variable choice gadgets
→ literal paths
→ clause unlock gadgets
→ final check path
→ finish reachable exactly when formula is satisfiable
```

## 7. Mario in the Nintendo hardness paper

For generalized Super Mario Bros, the paper proves that deciding whether the goal is reachable from the start of a stage is NP hard. The proof uses the general gadget framework and then implements each gadget using Mario mechanics such as Super Mushroom state, bricks, item blocks, Goombas, Firebars, and one direction movement constraints. ([ar5iv][2])

The Super Mushroom matters because big Mario has properties that small Mario does not: he is two tiles tall and can break bricks. The proof uses those state differences to enforce path constraints. Clause gadgets use a Star so that visiting a clause earlier enables safe traversal through hazards later on the check path. ([ar5iv][2])

The crossover gadget is one of the most important parts. A reduction often needs paths to cross in a planar level without allowing leakage between logical wires. The paper constructs such a gadget by exploiting Mario’s size state, bricks, narrow corridors, and traversal direction. ([ar5iv][2])

The result extends to Super Mario Bros 1 to 3, The Lost Levels, and Super Mario World, with modifications to gadgets where later games have different mechanics. ([ar5iv][2])

## 8. PSPACE and the difference between memory bounded and remembered worlds

The Nintendo paper also gives an important positive result: if the screen size or room size is bounded and the game forgets substantially off screen state, reachability can become polynomial time because the effective state space is polynomial in the level encoding. ([ar5iv][2])

This distinction is not cosmetic. Many game hardness results depend on whether the world remembers past actions. If visited enemies, opened doors, destroyed blocks, or moved objects persist globally, the game state can encode long computations. If off screen state resets, the model may lose the memory required for stronger hardness. ([ar5iv][2])

For PSPACE hardness, the paper uses a quantified Boolean formula style construction with door gadgets. Doors can be opened, closed, and traversed, which lets the level simulate repeated reevaluation of variable assignments and universal choices. ([ar5iv][2])

```text
NP style gadget
→ choose assignment once
→ check clauses once

PSPACE style gadget
→ change state over time
→ revisit logical structure
→ simulate quantified choices
```

## 10. Super Mario beyond NP hardness

Later work strengthened the Mario result. Demaine, Viglietta, and Williams showed that solving a generalized Super Mario Bros level is PSPACE complete, strengthening the earlier NP hardness result. They also distinguish between broad generalized levels and more realistic bounded screen models, where the complexity can be lower under explicit level encoding. ([erikdemaine.org][4])

This is useful when explaining the Nati Mendez topic because “Mario is hard” has two different meanings depending on the model. Under one model, Mario reachability is NP hard. Under a stronger memory rich generalized model, it can be PSPACE complete. Under a restricted model where off screen state is forgotten and the screen size is bounded, the problem can be polynomial time. ([ar5iv][2])

## 11. The HSP and Shor's algorithm for discrete log

Childs’s lecture explains the discrete logarithm problem and shows how it fits into the hidden subgroup problem. Given a cyclic group generated by g and an element x, the discrete logarithm is the smallest alpha such that g^alpha equals x. Computing g^alpha is efficient by repeated squaring, but no classical polynomial time algorithm is known for computing alpha in general. 

The lecture then recalls Diffie Hellman key exchange and states the classical security intuition: if an attacker can compute discrete logarithms, the attacker can recover the private exponents and derive the shared key. It also notes that the reverse implication is not fully settled in general. 

The hidden subgroup problem asks for a hidden subgroup H of a known group G, given oracle access to a function that is constant on cosets of H and distinct on different cosets. In abelian groups, there is an efficient quantum algorithm for the hidden subgroup problem. 

## 12. Discrete logarithm as a hidden subgroup problem

For discrete logarithm, Childs casts the problem as an abelian hidden subgroup problem over Z_N × Z_N. Define:

```text
f(alpha, beta) = x^alpha g^(minus beta)
```

If x equals g^a, then:

```text
f(alpha, beta) = g^(alpha a minus beta)
```

So f is constant along lines where alpha a minus beta is constant. The hidden subgroup is generated by pairs of the form:

```text
(0, 0), (1, a), (2, 2a), ..., (N minus 1, (N minus 1)a)
```

Finding that hidden subgroup reveals the discrete logarithm a. 

The quantum part uses a uniform superposition, evaluates the hiding function, measures the function register, applies the quantum Fourier transform, and obtains information from which the discrete logarithm can be recovered with good probability after repetitions. Childs states that the procedure works for any cyclic group with unique representation and efficient group operations. 

## 13. Cryptographic consequence of Shor style discrete log algorithms

The consequence is direct: finite field Diffie Hellman and elliptic curve Diffie Hellman rely on the assumed hardness of discrete logarithm. Childs’s lecture states that discrete logarithms can be calculated efficiently on a quantum computer, rendering protocols such as Diffie Hellman key exchange insecure. 

This does not mean classical Diffie Hellman is currently broken by ordinary computers. It means its security assumption is not quantum resistant. Long lived secrets protected by classical public key exchange face store now decrypt later risk if adversaries can record traffic today and later obtain a sufficiently powerful quantum computer.

## 14. Cross reading synthesis

Diffie and Hellman show how computational hardness creates cryptographic possibility. The Nintendo and Mario works show how ordinary looking interactive systems can encode hard logical search problems. Childs shows how quantum computation can collapse one of the central hardness assumptions behind classical public key cryptography.

```text
Diffie Hellman

modular exponentiation easy
discrete logarithm assumed hard
shared secret possible over public channel

```

## 15. Practical design rules

Use Diffie Hellman only with authentication. Plain key exchange does not authenticate the peer and is vulnerable to active substitution.

Use modern groups. Prefer well reviewed elliptic curve groups or standardized finite field groups with subgroup validation and safe parameter choices.

Bind the transcript. A secure key exchange should derive keys from the full protocol transcript, including identities, algorithms, public shares, context, and role labels.

Plan for post quantum migration. Classical Diffie Hellman and elliptic curve Diffie Hellman are not sufficient for long term confidentiality against future quantum adversaries.

When reading complexity claims, check the model. “Mario is hard” depends on whether levels are generalized, whether the screen is bounded, whether off screen state persists, and how the level is encoded.

Treat reductions as engineering tools. The gadget method is a useful mental model for protocol security too: local constraints compose into global behavior, and a tiny unintended transition can invalidate the proof.

## 16. Final takeaway

The deep connection across these readings is asymmetry. Cryptography wants functions that are easy for honest parties but hard for attackers. Complexity theory studies when search or reachability becomes hard. Quantum algorithms show that some hardness assumptions are model dependent. Diffie Hellman was revolutionary because it made public communication sufficient for shared secrets, but Childs explains why its discrete logarithm foundation is not stable against quantum computation. The Nintendo and Mario results provide a concrete way to understand reductions: a system with simple local rules can encode globally hard computation.
